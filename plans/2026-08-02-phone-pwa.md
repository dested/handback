# Handback on the phone — PWA capture intake

status: done (code shipped 2026-08-02; on-device QA outstanding)
date: 2026-08-02

## The ask

Open handback.dev on the phone, install it like an app, hit record, switch apps while
narrating, hit stop, and have a full walkthrough (keyframes + transcript + report) land in the
queue. "Go hard — PiP?? — give me something incredible."

## The platform verdict (checked 2026-08-02, MDN browser-compat-data)

**No mobile browser can capture the screen. Period.**

- `getDisplayMedia`: `version_added: false` on Chrome Android (exposed 72–88 but always threw
  `NotAllowedError`, then hidden so feature-detection works), false on Safari iOS, false on
  Firefox Android / Samsung Internet / WebView. Nothing shipped through mid-2026.
- Document Picture-in-Picture: desktop-only. Video PiP exists on Android but there is no stream
  to put in it — moot.
- So the "live recorder in a PWA" — the extension flow transplanted — is physically impossible
  on mobile. Any design that pretends otherwise is vapor.

**But the OS already ships the exact recorder we want.** Android (11+) Quick Settings → Screen
record with "Record audio: microphone"; iOS Control Center → Screen Recording with long-press →
Microphone On. Both capture every app, survive app switching, put a stop control in the system
shade, and burn zero browser battery. That is *better* than anything a web page could do — the
part the platform withholds from us is precisely the part it already does natively.

## The design: the OS records, Handback distills

The PWA's job is everything *after* capture — the half that is actually ours: keyframes,
transcription, polish, report, upload, routing. The phone flow becomes:

1. **Install** — handback.dev/phone → install prompt (Android) / Add to Home Screen (iOS).
2. **Record** — the OS screen recorder, mic on. Talk over anything: switch apps, scroll, rant.
   Stop from the notification shade.
3. **Share → Handback** — the PWA is a **Web Share Target**: the recording's Share button lists
   Handback in the Android share sheet; the video arrives with zero taps of file-picking. (iOS
   has no share-target for PWAs — there the app opens with a picker that reads straight from
   Photos.)
4. **Distill on-device (in the browser)** — the full extension pipeline, ported: seek-sampled
   keyframes with the same cell-hash dedup + `frameBudget` thin, audio → 16 kHz WAV chunks →
   `/api/ingest/transcribe` → `/polish`, report.md + recording.json built to the same shapes,
   two-phase declare → presigned PUTs → finalize. Indistinguishable in the inbox and the MCP
   brief from an extension walkthrough (minus page telemetry, which no mobile capture can have).
5. **Multi-clip** — each additional shared/picked video becomes the next `rec-NN` take.
6. **Voice-only mode** — the one capture the PWA *can* do live: mic-only MediaRecorder for a
   spoken gripe with no video. Same pipeline, zero frames.

Zero server changes: on first use the page mints an `hb_` token via `tokens.create`
(`autoTokenName('phone', …)`), stores it in localStorage, and speaks the same ingest protocol
as the extension. Quotas, rate limits, spaces, projects — all already enforced.

## Decisions

| Decision | Choice |
| --- | --- |
| Route | `/phone` — onboarding + intake in one, appLoader-guarded, app chrome |
| PWA scope | whole app; `start_url: /app`; shortcut "New walkthrough" → `/phone?new=1` |
| Share target | `POST /share-target` (multipart, `video/*` + `audio/*`), intercepted by `public/sw.js`, file stashed in IndexedDB, 303 → `/phone?shared=1` |
| Service worker | share-target interception ONLY — no caching, no offline shell (SSR app; staleness is worse than no offline) |
| Auth for ingest | mint `hb_` token via tRPC on first use; localStorage; auto re-mint on 401 |
| Transcription fallback | none on phone — 503 ⇒ ship without transcript, report says so (no wasm Whisper on a phone battery) |
| Keyframes | post-hoc seek-sampling of the (seekable) OS-recorded mp4; port extension dedup + budget exactly |
| iOS | no share target, no install prompt — instructions + Photos file picker; same pipeline (decodeAudioData handles mp4/AAC) |
| Live in-PWA screen capture / PiP | **rejected — platform-impossible** (see verdict above) |

## Limitations (honest)

- Long recordings: `decodeAudioData` buffers whole files; guide toward clips ≤ ~10 min
  (512 MB/file ingest cap is the hard stop).
- No click/console telemetry from other apps — `errorCount` 0, no forced keyframes; mobile
  walkthroughs are frames + voice, and that's inherent, not a gap.
- iOS HEVC ("High Efficiency" capture setting) plays on modern Chrome desktop (HW decode since
  107) but not universally; report tolerates it, viewer may black-frame on odd desktops.
- Installability/share-sheet is Chrome-on-Android's; Firefox Android users get the picker path.

## Build plan

- `src/lib/capture/*` — ported pipeline (pure modules, no UI): probe, frames, audio, transcribe,
  polish, report, recording-json, upload, context, token.
- `public/manifest.webmanifest`, `public/sw.js`, icons, `index.html` head, SW registration,
  share stash (`src/lib/pwa.ts`).
- `src/app/phone.tsx` — the intake UI per ui.md (editorial steps → destination row → clip list →
  staged distill progress → "Handed back." in approve green).
- Fable-owned glue: routes.tsx, autoTokenName iPhone/iPad detection, review, typecheck,
  cliffnotes.
