# Go-live checklist — what's required before strangers can sign up

> **Status: active** · opened 2026-07-30, the day inloop.dested.com went up on Drydock.
> Audit of the deployed app against "can we send this to people who aren't in the room."
> Each item names the file that proves it. Tick items off here; move the doc to `done` when the
> last blocker clears.

## The short answer

**Safe today:** hand the URL to people you can text — anyone whose password you're willing to
reset by hand, who'll tell you directly when something breaks.

**Not safe today:** a public sign-up link, a launch post, or anyone who expects to recover their
own account.

The multi-tenant boundary itself is sound (see [Already fine](#already-fine)) — what's missing is
account recovery, spend control, and a way for a new user to actually produce a gripe.

## Blockers (in the order they bite)

### 1. There is no password reset — and no email at all

`server/auth.ts` configures better-auth with `emailAndPassword: {enabled, autoSignIn}` and nothing
else: no `sendResetPassword`, no `sendVerificationEmail`, no email provider anywhere in the repo.

Consequences: the first user who forgets a password is locked out permanently short of a hand-edit
in the prod DB; a mistyped invite address is unrecoverable; nothing proves an address belongs to
the person who typed it. Invites are already link-only (the invite id **is** the token, 7-day
expiry) — that's fine among people you know and unacceptable at large.

**Fix:** wire an email provider (Resend), then better-auth's `sendResetPassword` +
`emailVerification.sendVerificationEmail`, and send the invite link instead of relying on copy-paste.
Needs a `RESEND_API_KEY` in SSM and a verified sending domain on `dested.com`.

### 2. Presigned PUTs carry no size limit and no quota

`presignPut` (`server/storage.ts`) signs `Bucket + Key + ContentType` only. Nothing constrains
object size, nothing caps gripes per org, nothing caps orgs per user. Declares are gated by
membership, but any signed-in user is a member of an org they created seconds earlier.

Consequence: with open sign-up, `/api/ingest` is a free, authenticated, unmetered storage endpoint
on your AWS bill. A real gripe is ~36 MB; nothing stops a 5 GB PUT.

**Fix (pick both):**
- Sign uploads with a length constraint — presigned **POST** with `ContentLengthRange`, or enforce
  the declared `bytes` server-side and reject a mismatched `Content-Length` at finalize.
- Per-org quota checked at declare time (total bytes + gripe count), plus an S3 lifecycle rule so
  abandoned prefixes age out.

### 3. The recorder isn't distributable

The extension is load-unpacked only — no Chrome Web Store listing. A stranger who signs up lands
in an empty inbox with no way to produce a gripe except `cli/push.ts` pointed at a folder they have
no way to record. Sign-up without the extension is a worse first impression than a waitlist.

**Fix:** ship it to the Web Store (see [below](#chrome-web-store-how-hard-really)). Start this
first — it's the only item with a queue you don't control.

### 4. No upload has round-tripped through S3 on prod

Deploy verified the DB path (`/healthz` probes it, the pre-deploy pushed the schema) and the HTTP
path (TLS, SSR). Nothing has exercised `presignPut` → browser PUT → finalize → `presignGet` from
the deployed container. The S3 keys in SSM are believed-good, not proven-good.

**Fix:** seed an owner + `ilp_` token against the prod DB (Drydock → Environment → "Connect from
localhost" opens 5432 to your IP), push one real gripe with `cli/push.ts --server
https://inloop.dested.com`, open it in the viewer, confirm every file loads. ~15 minutes.

## Should-fix before a public link

- **No rate limiting is configured** anywhere in the repo — not on sign-up, sign-in, or `/api/ingest`
  (the only limit is `json({limit: '10mb'})` on the ingest body). Credential stuffing and
  sign-up spam both walk straight in.
- **Pricing advertises tiers with no billing behind them** (`src/components/landing/pricing.tsx` —
  Free / paid rows). Either wire billing or relabel the paid tiers as coming-soon; charging copy
  with no charge path is the kind of thing people screenshot.
- **No error tracking or alerting.** You'd learn about a prod failure from whoever it happened to.
  The deploy has no post-deploy smoke check either.
- **ToS and privacy policy** — `/privacy` and `/terms` on the site. The Chrome Web Store requires a
  privacy policy URL regardless, so this is on the critical path for item 3 too. They must say
  what's stored, where (S3 us-west-2), for how long, and who can see it. **Re-read the privacy
  policy whenever the data flow changes** — in particular, moving transcription server-side adds a
  named subprocessor (see [`2026-07-30-transcription.md`](2026-07-30-transcription.md)) and the
  policy must be updated in the same release, not after.
- **Org deletion isn't built**, so a user cannot take their data back. Related: no per-gripe
  retention or expiry.

## Already fine

Worth stating plainly so it doesn't get re-audited: **the tenant boundary holds.** Every org and
gripe procedure in `server/router.ts` gates on `requireMembership` (delete requires `admin`,
role changes require `owner`); API tokens are stored as sha256 only and scoped to one org;
`/api/ingest` derives the org from the token rather than the request; the bucket blocks public
access and everything moves by presigned URL; ingest paths run through `isSafePath` before becoming
S3 keys. Deploys are green and reproducible on push (Drydock, see cliffnotes → Deploy).

## Chrome Web Store: how hard, really?

**Mechanically: easy. The wait and the disclosures are the work.**

- **Account:** one-time **$5** developer registration, near-instant.
- **Upload:** a zip of `extension/dist`. Already MV3 with a 128px icon and a real
  description — `bun run build:extension` produces the artifact.
- **Listing:** name, summary, detailed description, category, at least one **1280×800** (or 640×400)
  screenshot, icon. A couple of hours of copy and screenshots.
- **Review time:** commonly hours to ~3 days for a narrow extension. **This one won't be narrow**
  — expect longer, and expect at least one rejection round.

### What makes this submission slower than average

1. **`host_permissions: ["<all_urls>"]` plus a content script matching `<all_urls>`** — the broadest
   ask there is, and the single biggest driver of review time and rejections. Every permission needs
   a written justification, and broad host access needs the single-purpose story to be airtight.

   **Deferred, on purpose — do not do this pre-emptively** (Sal, 2026-07-30). The alternative is to
   inject the on-page dock via `scripting.executeScript` against `activeTab` when a recording
   starts, dropping the `<all_urls>` host permission and the always-on content script entirely.

   **When the time comes** — i.e. Google pushes back on the permission breadth, or the review sits
   for more than a couple of weeks, or a rejection cites host permissions — here is the change:
   - `extension/public/manifest.json`: delete the `host_permissions` array and the
     `content_scripts` block; `activeTab` + `scripting` are already granted.
   - `extension/src/background/`: on record-start, `chrome.scripting.executeScript` the dock into
     the active tab (and `insertCSS` for its styles) instead of relying on the `document_idle`
     content script. `web_accessible_resources` for `injected.js` stays as-is.
   - Consequence to accept: the dock exists only from record-start onward, not on every page. The
     `d`/`c`/`m`/`s` keys and the ink layer only work once recording has begun — which is arguably
     what a user expects anyway.
   - `injected.js` relay and the telemetry hooks need the same treatment; check every path in
     `extension/src/content/` that assumes it loaded before the user pressed record.
2. **Screen + microphone capture that leaves the machine.** This is sensitive user data by
   Google's definition, so a **privacy policy URL is mandatory**, along with the data-use
   disclosures and the Limited Use certification. See the ToS/privacy item above — same work.
3. **Remote code rules.** We're clean here and should say so: the ONNX runtime is *bundled*
   (`extension/scripts/copy-ort.mjs` stages the wasm into `public/ort/`, and the CSP is
   `script-src 'self' 'wasm-unsafe-eval'`). The Whisper **model weights** still download from
   huggingface.co on first use (`src/sidepanel/transcribeWorker.ts`) — weights are data, not
   executable code, but a reviewer may ask. Be ready to explain it, or vendor the model.
4. **The reviewer needs an account.** They cannot exercise the extension without one — it uploads
   to `https://inloop.dested.com` by default. Put working **test credentials in the "notes for
   reviewer" field**, or the review fails on "we could not test the functionality."

### Practical advice

- Publish **unlisted** for the alpha: same review, link-only distribution, no discovery, no store
  reviews from strangers. Flip to public when the go-live items above are done.
- Submit *before* fixing everything else — the queue runs in parallel with your work, and the
  first rejection tells you exactly which disclosure they want.
- Version bumps get re-reviewed, but updates to an already-approved listing are usually much faster
  than the first pass.

## Suggested order

1. Chrome Web Store submission (unlisted) — starts the clock on someone else's queue.
2. Prove the S3 round trip on prod (~15 min, removes the "unknown" from the deploy).
3. Privacy policy + ToS — needed by both the store and the public link.
4. Upload size cap + per-org quota.
5. Resend → password reset + email verification + emailed invites.
6. Rate limiting, pricing copy, error tracking.
